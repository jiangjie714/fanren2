### 3.3 M10 上线收尾（行政+配置，非代码）

**包体积（2026-10-05 分包改造完成后的现状）**：**主包 6.49MB + 分包 `subpackages/subres` 0.95MB**（总 7.44MB）。美术资源已整体迁入 subres 分包 bundle（`assets/subres`，加载走 `ThemeLib.loadArtBundle → assetManager.loadBundle('subres')`，全项目唯一图片加载入口），源 PNG 已就地 256 色量化（4.89MB→0.89MB，与构建后量化同算法、此前已验证目测无损）——**IDE 重建不再丢量化**（量化在源上，不在产物后处理）。`project.private.config.json` 的 `bigPackageSizeSupport` 仍由 build.mjs 幂等重写（预览期 8MB 上限保险）。**关键机制（逆向 builder 类型定义 + 产物 engine-adapter.js + 构建实验证实）**：
- 3.8 的 bundle「小游戏分包」压缩类型由构建面板「Bundle 配置」驱动；`.meta` 的 `userData.compressionType`（3.7 格式）不被读取；CLI 参数串无法承载（JSON 被 `;` 分割破坏/校验回退）；构建扩展 `onBeforeBuild` 收到的 options 是副本，改了也不传导（已实验证实，`outputName` 对照）。
- **生效方案 = 项目构建扩展 `extensions/subres-pack`**：`onAfterBuild` 钩子（产物落盘后的最后阶段，CLI 与 IDE 构建都执行）按引擎官方布局做磁盘重组——`assets/subres → subpackages/subres` + `game.json.subpackages:[{root:"subpackages/subres",name:"subres"}]` + `src/settings.json` 的 `assets.subpackages:["subres"]`。运行时契约（engine-adapter.js 明文可证）：引擎读 settings 的 subpackages 名单，对该 bundle 先 `tt.loadSubpackage({name})` 再从 `subpackages/<名>/config.json` 加载。build.mjs 末尾 `verifySubpackageLayout` 校验三处声明，缺一即退出非零（防扩展失效静默退回单包）。
- 已确认无效路径（勿再试）：CLI 参数 separateEngine/includeModules、settings/v2/packages/builder.json 的 packages 配置、profiles/v2/packages/builder.json 的 BuildTaskManager.taskMap（CLI 构建一律新建任务，不读已存任务）、构建扩展内改写 options。
- **预览（扫码预览，上限 8MB）**：6.49MB ✅ 当前即可用。
- **真机调试/发布（4MB 硬上限）**：✅ **已达标（2026-10-05 本会话完成）**——经 CDP 连入编辑器（`--remote-debugging-port=9333`）执行两步：①直接改 `settings/v2/packages/engine.json`（功能裁剪的真实存储，GUI 勾选写的同一文件）关闭 physics-2d/spine/dragon-bones/tiled-map/video/webview（grep 全码零依赖）；②真机产物用 `node tools/douyin-editor-build.mjs` 构建（封装 CDP：builder 内部消息 `Editor.Message.request('builder','add-task', options)` = 面板「构建」按钮的实现，带 `packages['bytedance-mini-game'].separateEngine=true` + 真实 AppID + subres bundleConfigs，构建后自动补 open-data-context/urlCheck 注入 + 体积把关）。**结果：引擎 5.85MB→452KB（功能裁剪贡献大头），主包 1.18MB + 分包 0.95MB（总 2.12MB）**；产物 game.json 声明官方引擎插件 `plugins.cocos v3.8.8`（provider tt8bf0fd4d14fb3db712，模拟器/真机首次使用如提示插件未授权，去抖音开发者平台该 AppID 下添加即可）。裁剪后引擎经 web 全流程回归（m7/m8/m9 全页面）验证无缺失模块。**抖音分包还有两个坑（已修）**：①校验器要求每个分包根目录必须有 `game.js`，缺失报 `should have game.js` 编译错误；②`game.js` 不能是空桩——`tt.loadSubpackage` 完成后平台会执行分包 game.js，其职责是 `require('./index.js')` 注册 bundle 的 SystemJS 模块（含 `virtual:///prerequisite-imports/subres`），空桩会报 `Unable to instantiate virtual:///prerequisite-imports/subres` 且美术全空。`extensions/subres-pack` 钩子按正确内容自动写入，build.mjs `verifySubpackageLayout` 亦把关。**抖音开发者工具模拟器已实测通过**（CDP 8488 重载取证：引擎插件 inject success、场景加载、分包美术正常渲染、无 subres 报错；日志仅剩引擎插件内部的 `meta request error`（平台插件自检噪音）与引擎 info 码）。⚠ add-task 的任务记录持久化在 `profiles/v2/packages/builder.json` taskMap（跨重启保留，面板任务历史可见），但 `query-tasks-info` 是会话级接口（重启后返回空）；⚠ **CLI 构建（build.mjs）拿不到 separateEngine，产物主包 ≈4.68MB 且在抖音开发者工具模拟器中白屏**（2026-10-06 实测复现与修复）：引擎未分离（`cocos-js/cc.js` 3.9MB 单文件）、缺 `custom-pipeline.js` 分块、`game.json` 缺 `plugins.cocos` 官方引擎插件声明。**CLI 构建只能当作「代码能否编译通过」的冒烟检查，产物一律用 `node tools/douyin-editor-build.mjs`（IDE 构建，主包 1.35MB + 分包 3.29MB，形态与模拟器兼容）**。

### 3.6 M14 秘境试炼（✅ M14-1~5 全部实现，2026-10-07）

**目标**：解决「不够上瘾 / 广告绑定弱」。诊断出四条结构性问题：P1 爽感峰值被攒机缘锁死（有技巧的手操玩法一天合计不足 1 分钟）｜P2 最爽的时刻惩罚最重（突破失败修为清零）｜P3 三个止损型广告全绑定在负反馈时刻｜P4 心流被每日次数硬限主动切断。

完整规格见 **[docs/superpowers/specs/2026-10-07-秘境试炼-design.md](superpowers/specs/2026-10-07-秘境试炼-design.md)**（含逐条数值口径、存档 v6 模型、测试清单、实现分期）。要点：

1. **把「心魔幻境」升级改造为「秘境试炼」**（非并列新玩法，避免两个 15 秒接雨滴玩法互抢注意力）。**沿用幻境评分公式不变**（金×4+连击×2−红×3，0–200）→ M9b 周榜 KV `illusion_week`、子域协议、#31 两条幻境成就**全部零改动**，不给尚未真机验证的社交管线叠加风险。
2. **A 体力经济**：上限 10 / 15 分钟回 1 点（惰性时间戳结算，无后台定时器）+ 三主题按日轮换（灵雨 ×1.0 / 劫云 ×1.3 成排 / 幻心 ×1.15 落速随机）。
3. **B 连胜轨**：达 60 分 +1 连，倍率 1.0→2.5（封顶）；中断可看 `trialRevive` 护持——**全套点击意愿最高的广告点**（玩家失去的是具体的「5 连」而非抽象增量）。
4. **C 段位轨（赛季制）**：段位分 `+= max(0, floor((score-60)/5))`，六段阈值 0/200/600/1400/2800/5000，周一按本周最高段位发周奖后清零重冲。刻意选赛季制而非「衰减 50%」——后者稳态值 = 周增量/0.5，重度玩家约 4900 会常态化顶到超凡，段位失去区分度。
5. **D 道心（改造 #3）**：失败修为改扣 30%（不再清零）+ 道心 +1（广告 +2），每层 +5% 成功率；**只给概率加成、不给「必成」**，避免把冲击高境界变成确定事件。
6. **产出改造**：秘境改为主产**灵材**、灵石减半。理由：① balance 护栏②日净收入已 2620–5137，满额产灵石必击穿 6000；② 灵材是 M13 稀缺痛点（典型一日仅 2–3 个）；③ 形成「打秘境→得灵材→炼丹变强→打更高难度」正循环，与 M13 联动而非又一个孤立刷灵石口子。
7. **广告位 7 → 10**：`trialStamina`（体力+5，每日 3 次）/ `trialRevive`（连胜护持）/ `doubleReward`（通用结算翻倍，含活跃度宝箱）。

### 6.4 踩坑记录（复用本管线前必读）

1. **生成图的"品红"不是品红。** 提示词写 `#FF00FF`，实际产物会在 `#D01273`（玫红）与 `#FD21FF`（品红）之间随机漂移。而技能处理器 `remove_bg_magenta()` 把 key color **硬编码为 (255,0,255)**：对玫红的欧氏距离约 150，恰好卡死在 `threshold=100` 之上，**背景一个像素都删不掉**。因此 `clean_watermark.py` 的归一化是必需步骤，不是优化。
2. **品红家族判定不能用 `r > b`。** 纯 `#FF00FF` 的 R 与 B 相等，用大小关系会漏判一半。正确特征是「绿通道远低于红与蓝」。
3. **每张生成图右下角都有固定水印。** bbox 在 1024×1536 上恒为 x[889,1024] y[1456,1536]，按比例锚定即可。漏处理的后果是水印被当作精灵主体抠进游戏。
4. **换图必须重算 `.meta` 的 trim。** `subMetas.f9941.userData` 的 trimX/trimY/width/height/vertices/uv 是按**旧图** alpha 包围盒算的，不重算会按旧包围盒裁错。
5. **覆盖已有资产必须沿用原 UUID**，否则 asset-db 视为新资源、旧引用悬空。`install_assets.py` 自动读取旧 meta 的 uuid。
6. **绝对不能让资产改扩展名（`.png` → `.jpg`）—— 这是本项目踩过最贵的一脚。** 起因是体积：全屏厚涂插画存全彩 PNG 单张 1.65MB，实测 JPEG q92 只要 346KB、256 色 PNG 491KB，于是把三张背景改存 `.jpg` 并把手写 meta 改名为 `bg_home.jpg.meta`。结果**构建不报任何错、产物里也确实躺着 `…fd49.jpg`，但运行时背景完全不显示**。根因：asset-db 的 `library/` 索引里该 uuid 记录的是旧路径 `bg_home.png`，构建据此生成的 native 引用仍是 `.png`，引擎去请求 `…fd49.png` → 404 → spriteFrame 静默加载失败。**构建工具链不校验这个不一致**，只能靠浏览器 `performance.getEntriesByType('resource')` 抓不到该图才发现。结论：格式调整一律通过**量化（`quantize: 256`）**实现，文件名与扩展名保持不变；`install_assets.py` 现已支持 `quantize`，不透明图走 RGB+MEDIANCUT、含透明像素走 RGBA+FASTOCTREE。三张背景最终为 491/510/393 KB。
7. **宝箱必须按 4:3 裁切。** 场景显示框是 190×150 / 206×164，塞 1:1 素材会横向压扁 28%。
8. **道具不要用碎片清理。** 天道宝盒周围的金色火花是独立连通块，`--min-area 40` 一次删掉 72 块。道具类应 `--min-area 0`，只做 despill。
9. **`generate2dsprite process` 的 `fit-scale`（默认 0.85）会把主体统一缩放**，三个尺寸不同的宝箱输出的主体宽度会全部变成 cell 的 85%（1024 cell → 870px）。这会让主体宽度趋同、只保留高度比例差 —— 设计上是好是坏取决于用途，但**必须知道它发生了**。
10. **量化（`quantize`）之后不能再指望「自动 trim」—— 曾有 bug。** `install_assets.compute_frame` 旧实现写的是 `image.getchannel("A") if image.mode in ("RGBA","LA") else None`；而量化产物是 **P 模式**（调色板 + `transparency` 索引），于是 alpha 恒为 `None` → bbox 退回整图 → `trimX/trimY = 0`、`width = rawWidth`。**不报错、不崩、图也显示**，只是立绘比同批非量化资产多一圈透明边距，在固定节点尺寸下**主体偏小约 9%**（第 9 章立绘曾整体比第 1–8 章小一号）。已修为 `P + transparency` 时先 `convert("RGBA")` 再取 bbox。全仓复查：仅 `bg_home/bg_rain/bg_result` 三张全屏背景命中，且背景本就该整图 trim，无副作用。**排查手法**：比对 meta 的 `trimX/trimY/width` 与真实 alpha bbox（`Image.convert("RGBA").getchannel("A").getbbox()`），不一致即命中。
11. **`clean_watermark.py --mode plain` 是空操作，不是「只去水印」。** 文档字符串写「只去水印，不动底色」，但代码是 `if resolved == "magenta" ... elif resolved != "plain": inpaint(...)` —— `plain` 把两个分支都跳过了。**背景插画误用 `--mode plain` 会原样保留右下角「AI生成 WORKBUDDY」水印**（构建与运行都不报错，只有看截图才发现）。正确用法是 `--mode auto`：非品红底图会自动解析成 `inpaint`。

### 7.3 设计令牌（乘算 tint 的坑）

原代码在 10 个场景里散落 55 处 `new Color(14, 20, 52, 230)` 这类 navy 硬编码。
**换色板只改 `ThemeLib` 是没用的** —— 这些 tint 是**乘算**，会把新画的玄墨紫 9-slice
再乘成脏蓝黑，表现为「一半新一半旧」。

收编工具：`python tools/art-rebuild/tokenize_colors.py`（带 `--dry-run`）。

关键认识：**乘算 tint 只能调明度，改不了色相**。紫色面板乘任何颜色都变不出绿/红。
所以：

- 层级差异改由近白暖色令牌表达 —— `tintPanel` / `tintDeep` / `tintCard` / `tintSeat` / `tintMuted`。
- 「突破成功 / 突破失败」这类必须读出色相的容器，用 `ThemeLib.washedPanel()`：
  底层保持标准 9-slice（墨边金线完整），上层叠一块内缩的语义色晕。
  色相之外**文案本身**就是冗余编码（红绿色盲可读）。

- **9-slice 程序化重绘**（`paint_ui.py`）：7 件（panel×2 / btn×3 / progress×2）。
  尺寸与 border 全部沿用原值（panel 22、btn 34、progress 18），**场景代码零改动**。
  为什么不用 AI 生成：九宫格要求四角对称、边缘连续、中间可任意平铺，AI 总在中间带
  装饰，拉伸必出接缝，且 border 无法精确控制。
- **19 个图标**（AI 生成 + 底板统一）：`icon_{back,box,jiyuan,lingshi,xiuwei,quest,ludao,collection,settings,shop,ad,close,lock,illusion,juling,purify,rune,timer,expedition}`。

### 7.5 3 个新踩坑（复用本管线前必读）

1. **`tint` 是乘算，不是叠加。** 想给面板换色相只有两条路：换资产，或叠一层色晕。
   给紫色底 tint 绿色只会得到更暗的紫。
2. **「抬 alpha」只能按权重加权，不能整块 Math.max。** 若写成
   `alpha = max(alpha, floor)` 而 floor 在低权重处仍算出 255，透明角落会变成
   **不透明黑方块** —— 图标拼图上直接看到一格格黑底。
3. **自动 trim 会按 alpha 包围盒裁掉 9-slice 的透明圆角**，导致 border 坐标系整体错位。
   9-slice 资产必须 `trim=False`（`install_assets.py` 已支持 `"trim": false`）。

## 八、UI 版式与可读性检修（2026-10-05）

配色落定后对 10 个页面做了一轮逐页巡检，发现并修掉了一批**真实存在**的版式缺陷。
本章只记录「为什么错、错在哪、怎么修的」，配色口径见第七章。

### 8.1 共同根因：`align:'left'` + `width` 的锚点语义

`label(parent, text, size, { align: 'left', width: W })` 的语义是「在一段**定宽盒子内**左对齐」，
而盒子本身仍是**居中锚点** —— 文本左边缘因此落在 `x - W / 2`。

代码里 22 处 `align:'left'` 调用几乎都把 `x` 当成左边缘传，产生三类缺陷：

| 症状 | 实例 |
| --- | --- |
| 首字被容器边缘裁掉 | `QuestScene` 任务名左缘 −327（卡片边 −330）；`ExpeditionScene` 的「产」字 |
| 同一容器内各行左边界互不相同 | `ExpeditionScene` 目的地卡三行分别是 −276 / −278 / −298 |
| 文本横向越界，压到邻居身上 | `LudaoScene` 榜卡 `x=−130, width:540` → 左缘 −400，比卡片左缘 −330 还左 70px |

**修法**：`ThemeLib` 新增 `labelL()`，用 `anchor(0, 0.5)` 把 `x` 定义成**文本左边缘**，
行内排版只需写「容器左缘 + 内边距」。已有 `align:'left'` 调用按页逐步迁到 `labelL`。

### 8.4 3 个新踩坑（复用前必读）

1. **headless 截图的「等毫秒」≠「等动画跑完」。** headless Chrome 的 rAF 会被节流，
   Cocos 补间虽按墙钟算 dt、dt 却有上限钳制 —— 实测 1200ms 墙钟只推进约 0.1s 动画时间。
   曾因此把「卡片入场淡入到 55% 不透明度」误判成「卡片面板半透明、背景色透出来」，
   并据此展开了一整轮错误排查（甚至打算重做面板资产）。**结论：截图前必须 `waitFrames(n)`。**
2. **`spritePanel(parent, …)` 把 Sprite 挂在新子节点上**，`parent.getComponent(Sprite)` 恒为 null。
   想在运行时改面板 tint 必须先给子节点起名（约定 `bg`）再取。
   `BoxScene` 的锁定态面板灰置因此**静默失效**两轮：只有宝箱图被灰掉，卡片底纹丝不动，
   而代码里那句 `if (cardSprite)` 看起来完全正常。
3. **构建产物里全局 `cc` 不保证导出 `UITransform`**，探针脚本要走 `node._uiProps.uiTransformComp`；
   否则 `getComponent(cc.UITransform)` 得到 null，属性读出来全是 `?`。
